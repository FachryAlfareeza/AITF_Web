## Design decisions (made here, grounded in the code I read)

1. **TOR storage keying.** RAB blobs are stored under three keys: `submission.id`, `submission.ticketNumber`, and the RAB `fileName` (see `handleAiSubmit` in `frontend/src/components/SatkerView.tsx` calling `storePdfBlob(newSubmission.id, rabFile)` / `.ticketNumber` / `.rabFileName`). `PdfPreviewModal` resolves a blob by trying `[ticketNumber, submissionId, fileName]` in order (see `resolvePdf` lookupKeys in `frontend/src/components/PdfPreviewModal.tsx`). To guarantee TOR and RAB blobs never collide, store TOR under `tor:`-prefixed keys: `` `tor:${submission.id}` ``, `` `tor:${submission.ticketNumber}` ``, and `` `tor:${torFileName}` ``. To preview the TOR, pass those same prefixed values into `PdfPreviewModal` (`submissionId={`tor:${sub.id}`}`, `ticketNumber={`tor:${sub.ticketNumber}`}`, `fileName={torFileName}`) so the modal's existing retrieval + `generateFallbackRabPdf` fallback chain finds the TOR blob, not the RAB one. Rationale: reuses the existing keying/preview/fallback pattern with zero changes to `pdfStorage.ts` or `PdfPreviewModal.tsx` internals.

2. **TOR required vs optional.** Type fields are OPTIONAL (`torFileName?`, `torFileSize?`, `torPdfDataUrl?`) so previously-stored submissions (which have no TOR) still parse — `loadSubmissions` in `appStorage.ts` does not validate TOR fields, so older records stay valid. In the NEW submission form, TOR is REQUIRED (block submit and show an error if TOR is missing), mirroring the existing RAB "wajib unggah" gate in `handleAiSubmit`. This matches the task's default recommendation.

3. **TOR validation.** Reuse the exact magic-bytes check already present for reupload in `SatkerView.tsx` `handleReuploadFileChange`: read `file.slice(0, 5)`, require `file.name.toLowerCase().endsWith(".pdf")` AND `new TextDecoder().decode(header) === "%PDF-"`. The form's current RAB input (`handleRabUpload`/`handleDirectFileUpload`) only checks via the `accept=".pdf"` attribute; the TOR input will use the stricter magic-bytes check, and this is also the opportunity to document that RAB keeps its current behavior (do not change RAB validation in this phase).

4. **No analysis on TOR.** The existing local demo analysis (`inspectUploadedRabDocument` in `frontend/src/utils/pdfInspector.ts`, `runAiRabAnalysis` in `frontend/src/data/defaultCriteria.ts`) continues to run on the RAB exactly as today. TOR is uploaded, stored, and previewable only. Do not alter the analysis logic or the RAB fallback chain.

5. **Requirement 2 (acuan for verifikator) is already functional — this is a VERIFY-and-fix task, not an extend task.** Evidence: `frontend/src/App.tsx` routes `menu_acuan` to `SuperAdminView` passing `permission={currentPermission}`, where `currentPermission = ROLE_PERMISSIONS_MATRIX[stdKey]?.[activeRole]`. For verifikator, `ROLE_PERMISSIONS_MATRIX.menu_acuan.verifikator === "E"` (in `frontend/src/types.ts`), so `SuperAdminView` receives `permission="E"`. Inside `SuperAdminView`, `isEditable = permission === "E"` gates every edit control: the "Unggah Peraturan Baru" button, the upload form (`regSubTab === "unggah_peraturan"`), the reindex button, and `RegulationCardList`'s `isEditable` (which gates toggle/edit/delete). `Sidebar.tsx` lists `menu_acuan` for verifikator with an "E" pill. So acuan add/view/activate-deactivate/remove already work for verifikator through matrix-driven rendering. There is NO superadmin-only hard check to relax. Acuan PDFs are stored as `pdfDataUrl` (base64) on `RegulationDocument` via `appStorage.saveRegulations`/`savePdfMetadataList`, and `PdfPreviewModal` renders base64 data URLs (step 1 of `resolvePdf`) — no change needed. The only defensible fix is a copy nuance, handled in item 5.

6. **Copy softening (keep light).** Soften a few user-facing headings/buttons in `SatkerView.tsx` that present the local demo analysis as a finished real-AI verdict, to read as a demo/prototype analysis in Indonesian (e.g. "analisis demo", "hasil sementara prototipe"). Do NOT rewrite analysis logic, variable names, field names (`aiStatus`/`aiScore`/etc. stay), or the PMK/criteria domain text. Keep scope to the clearly AI-verdict-claiming strings listed in item 5.

## Notes / assumptions

- `formatFileSize` (in `frontend/src/utils/formatUtils.ts`) is already imported in `SatkerView.tsx` and is used for both RAB and TOR size strings.
- `appStorage.savePdfMetadataList` strips large/blob `pdfDataUrl` values from the RAB field before writing to localStorage; TOR's `torPdfDataUrl` is a separate field and is NOT stripped by that helper, but the authoritative TOR bytes live in IndexedDB under the `tor:`-prefixed keys, so preview still works after reload via `PdfPreviewModal`'s IndexedDB lookup. This mirrors how RAB survives reload (its blob URL is stripped from localStorage but the blob persists in IndexedDB). No change to `appStorage.ts` is required.
- Requirement 2 needed no extension; the plan records the verification explicitly (item 7) so the implementer confirms rather than assumes.
